# 分片上传：数据库幂等兜底

## 问题与最终行为

原实现先保存媒体记录，再把完成凭据写入 Redis。数据库写入成功后进程中断、提交响应丢失或 Redis 写入失败时，重试可能重新合并并保存一条媒体记录。

现在新完成的分片上传会在同一个 Spring 数据库事务中写入 `media_files` 和 `chunk_upload_completions`。完成凭据以 `upload_id` 为主键：即使 Redis 锁未能阻止重复执行，数据库唯一约束也会让失败一方的媒体插入回滚。正常锁仍保留，用于避免重复合并与对象上传的开销。

已完成的上传优先查询数据库；即使 Redis 完成缓存和上传元数据丢失，完成请求仍返回原媒体，状态查询返回全部分片序号，迟到的分片请求不再写入对象存储。每个入口仍检查原用户归属。

完成凭据在媒体删除后继续保留，不设置级联删除：旧上传请求返回文件不存在，不能重新创建已经删除的媒体。

## 文件与部署

- `V4__persist_chunk_upload_completions.sql`：新增完成凭据表，不修改已有迁移。
- `ChunkUploadRepository`：原子写入媒体和完成凭据；通过 Spring 代理提供事务。
- `ChunkUploadService`：数据库完成记录优先、Redis 完成缓存尽力更新、唯一冲突后返回已提交的记录。
- `ChunkUploadRepositoryTest`：实际 SQL、MyBatis 和 Spring 事务测试。
- `ChunkUploadServiceTest`：故障注入与接口服务行为回归。

部署时先备份数据库，再启动新版后端，由 Flyway 应用 V4；数据库账号需要建表权限。接口路径和响应格式保持兼容，前端无需调整。上线后如需回退应用版本，应保留新增表；旧版应用不会使用这张表，也不具备新增的幂等保障。

## 验证场景

1. 数据库提交完成但确认丢失：重试只返回原记录，不再次保存或删除原视频对象。
2. Redis 完成凭据写入失败、元数据丢失：完成、状态查询和迟到分片重试仍识别已完成上传。
3. 同一上传并发写入：唯一约束只允许一条完成凭据，失败事务新增的媒体记录回滚。
4. 完成凭据插入失败：媒体插入同时回滚，后续可重新完成。
5. 跨用户访问、删除后旧请求重试：均不能复用上传创建新媒体。

数据库自动化测试使用测试范围的 H2（MySQL 模式），执行原 V1 和新增 V4 建表语句，验证真实 SQL 约束与 Spring/MyBatis 事务参与。它不代替真实 MySQL 的全量 Flyway 迁移和生产环境验证。

## 边界

- 保障范围是同一 `uploadId`，同一个文件重新初始化得到不同 ID，仍视为新上传。
- 升级前已经完成的上传没有持久化完成凭据；仍兼容其有效期内的 Redis 凭据。旧数据无法从媒体记录可靠反推出原 `uploadId`，本次不猜测回填。
- 未完成上传的分片状态继续存放在 Redis，Redis 元数据丢失时仍需重新初始化。
- 对象存储不参与数据库事务。唯一冲突已知回滚时清理本次多余对象；其他数据库故障可能发生在 COMMIT 确认阶段，提交结果不确定，因此保留对象以避免删除已经提交的视频。失败遗留对象和分片的持久化清理属于后续独立工作。
- Redis 缓存写入失败后的首次请求也可以成功；缓存故障记录告警日志，不撤销已提交的完成记录。
