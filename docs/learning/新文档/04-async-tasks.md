# 04 为什么分析任务需要排队

视频分析可能经过音频处理、识别、检索和多轮模型调用。用户提交目标后，后端先受理任务，再由消费者处理。接口返回受理成功，不表示分析已经完成。

## 消息队列传递什么

队列传递的是任务信息，例如媒体编号、动作、目标、模式和内容标识。视频对象已经放在文件存储里，不需要把整段视频塞进消息。

`AnalysisDispatchService` 检查重复提交和配额，再通过 RocketMQ 投递。`VideoAnalysisConsumer` 消费消息，检查已有结果、协调共享计算、执行业务并处理失败。

把队列理解为待办清单：接待员登记工作，工作人员按能力处理。排队可以缓解瞬时压力，但不会凭空增加服务器算力。

## 为什么还要幂等

客户端可能重复提交，消息也可能再次投递。比如消费已完成，但确认没能成功到达，系统就可能再次处理同一消息。业务需要先判断是否已有可复用结果，防止重复计算和重复收费。

本项目任务隔离会考虑媒体、目标和模式；相同视频的两个不同问题不能随便当成同一个结果。内容哈希用于识别可复用的计算范围，与用户的任务身份需要区分。

## 重试和失败重放

短暂网络错误可能重试成功，错误配置和无效输入则不一定能靠重试解决。当前消费者有有限重试及失败处理，管理员可以查看失败任务并重新投递。

重新入队是再次受理，不等于立即修复；应先理解失败原因，并确保重复执行不会破坏结果。

## 代码入口与边界

先读 [AnalysisDispatchService](../../../server/src/main/java/com/example/server/service/AnalysisDispatchService.java)，再读 `VideoAnalysisConsumer` 和 `FailedAnalysisTaskService`。重点找：重复判断在哪里、何时记录失败、什么情况下抛异常让消息重试。

当前 Redis 活跃标记和 MQ 发送分开执行。数据库任务表、Outbox 与超时巡检是后续可靠性方向，不能因为已经用了 MQ 就认为受理和投递天然是一个事务。
