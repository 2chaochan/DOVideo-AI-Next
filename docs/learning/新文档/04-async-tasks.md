# 04 从同步请求走向异步任务

一次健康检查只需要很少的计算，但课程视频分析可能需要下载、解码、识别和多次模型调用。用户点击按钮后，如果一直占着原 HTTP 请求等待，可能遇到超时，也会占用请求处理资源。

## 1 同步和异步描述等待关系

同步处理可以简化成“接到请求 → 做完工作 → 返回结果”。异步任务则是“接到请求 → 登记和安排工作 → 返回受理信息”，工作在后续继续完成，客户端再获取进度和结果。

异步不会让五分钟的计算自动变成五秒，也不等于无限开线程。它改变的是提交方与执行方的等待关系。

## 2 为什么引入消息队列

队列暂存待处理消息。生产者把任务交进去，消费者从中取得任务并执行。这样接收请求的速度和实际处理能力可以分开，瞬时请求较多时先形成积压，而不是全部立刻占用模型和媒体进程。

本项目 `AnalysisDispatchService` 是提交侧，`VideoAnalysisConsumer` 是消费侧，RocketMQ 是消息中间件。队列的消息主要保存任务身份和目标，视频文件仍在 MinIO 中。

教学消息如下，字段名对应任务类，值只是示例：

```json
{"mediaId":42,"action":"START_ANALYSIS","contentHash":"example-hash","userGoal":"整理前序遍历步骤","mode":"LEARNING"}
```

消息让消费者知道“处理哪条视频、做什么”，消费者再读取持久化数据和文件。

## 3 为什么消息处理不能假设只执行一次

假设消费者已经保存结果，但在确认消息前退出。消息可能再次被投递。若第二次无条件再调用全部模型，就会浪费资源，甚至改变结果。

因此业务要检查已有结果、任务状态和检查点。幂等不只用于上传；耗时智能体任务也要区分“需要执行”“已经完成”“上次做到一半”。同一视频的不同目标和模式还要正确隔离。

## 4 重试要与错误原因联系

网络短暂抖动可能重试成功；模型名称填错则通常需要修配置。无限重试会让失败任务长期占资源。当前消费者采用有限重试与失败记录处理，管理员能够重新投递失败任务。

重放的意思是再受理一次，不是保证这次一定成功。排查时先看失败发生在解析、检索、模型还是持久化阶段。

提交侧也有独立故障窗口。Redis 活跃标记、MQ 投递和数据库写入不会因为写在一个 Java 方法里就自动成为一个事务。持久化任务表和 Outbox 是后续可以学习的改造方向，当前不能把它们当成已经实现的能力。

## 5 页面如何知道进度

普通查询由客户端发起请求获取当前状态；SSE 则允许服务端通过持续的 HTTP 响应发送事件。本项目通过任务事件服务发送阶段信息，让页面知道已排队、处理中或已结束。

进度事件是展示通道，检查点是恢复依据，两者职责不同。页面断开不应等同于已经撤销所有后台任务；实际取消能力需要专门设计并查看实现。

## 6 阅读任务和答案

阅读 [AnalysisDispatchService](../../../server/src/main/java/com/example/server/service/AnalysisDispatchService.java)，找到重复判断、配额与 `convertAndSend`。再读消费者，找处理成功、准备重试、写失败记录的分支。

问：队列越来越长，增加客户端请求线程能解决吗？答：通常不能，瓶颈可能在消费者、CPU、磁盘或外部模型配额，接单更快甚至会增加积压。

问：受理接口返回 202，能立即显示最终学习笔记吗？答：不能，它表示已受理，客户端仍需根据阶段状态取得最终结果。
