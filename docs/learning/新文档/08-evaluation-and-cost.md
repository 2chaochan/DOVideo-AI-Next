# 08 通过质量 延迟和费用判断 Agent 改进

修改提示词后，回答更长、更像一篇文章，并不能单独证明系统变好了。用户要的是正确覆盖目标、能核对证据、在可接受时间和成本内得到结果。

本章先区分流程是否运行成功，再讨论答案质量与资源消耗。

## 1 结构检查 内容质量和用户价值

结构检查可以验证必需字段是否存在、时间是否越界。内容质量需要判断结论是否受到材料支持，是否遗漏用户要求。用户价值还涉及输出是否便于复习或决策。

例如答案包含合法时间戳，但引用片段讲的是后序遍历，结论却说前序，这是结构看起来完整而内容仍有问题的例子。只统计 HTTP 成功率看不到这种错误。

Critic 属于任务内部检查，离线评估则在一组预先准备的任务上比较表现。二者都需要合适的材料和标准，不能把某模型对自己的肯定当成独立正确率。

## 2 先建立可重复的评估任务

项目的 [golden-video-tasks.json](../../../server/src/main/resources/evaluation/golden-video-tasks.json) 包含上下文、目标和预期关键词等字段。例如课程案例提供 120000 到 180000 毫秒的材料，目标是生成前序遍历学习笔记。

这些固定输入方便比较版本。`AgentEvaluationService` 和 `OfflineAgentEvaluationRunner` 提供评估相关入口，但具体评分能证明什么，要看规则。关键词命中说明覆盖了一些词，不自动证明论证正确或证据充分。

自己的评估表可以逐条记录：目标覆盖、证据相关性、遗漏、耗时和估算消耗。表中的判断应该能追溯到输入和输出。

## 3 Token 和费用怎样估算

模型输入和输出通常都会产生消耗。为一次任务估算费用，需要知道各次调用的输入、输出量，以及相应单价。简化计算关系是：输入量乘输入单价，加输出量乘输出单价，再统一计量单位。

项目 `AgentTelemetry` 使用估算 Token 和配置价格形成估算费用。它不是供应商账单；价格未设置、Token 估计有偏差或模型计费规则不同，都会影响数值。代码里的 0 也可能表示某项费用限制未启用，不能自动理解为调用免费。

## 4 限流和预算分别限制什么

限流控制一段时间允许多少请求，例如避免一个用户持续快速提交。单任务预算控制一次工作允许多少轮、多少时间、多少估算 Token 或费用。

两次请求的调用数量可能不同，所以每分钟请求限制不能替代单任务预算。反过来，单任务很便宜但请求无限增加，也可能耗尽系统资源。

`AgentExecutionBudget` 管理执行时间范围，循环还检查轮次和估算消耗。达到边界后必须按实现结束或报错；不能为了通过 Critic 无限继续。

## 5 怎样设计一次提示词实验

固定视频片段、用户目标、模式和评估标准，只改变提示词中的一个因素。保存模型名称、配置、版本与输出。由于生成存在波动，有条件时对相同输入重复运行，观察变化范围。

例如实验目的是减少没有证据的结论，就应检查无证据结论数量和正确拒答情况，而不只是观察篇幅变化。还要记录质量改善是否带来明显延迟和消耗增长。

## 6 练习与答案

问：A 版本平均快两秒，B 版本少了一个关键事实错误，哪个更好？答：需要依据使用场景和质量门槛判断，先分别记录事实与指标，不能把所有目标压成一个未经说明的分数。

问：为什么一个用户请求可能对应多次模型调用？答：路由、计划、执行、检查与修正可能分别调用模型，需要把整条链路的消耗统计起来。
