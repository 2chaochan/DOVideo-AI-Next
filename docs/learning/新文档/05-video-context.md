# 05 从视频文件到有时间证据的上下文

视频 42 已经存好，消费者开始处理。用户要的是“整理前序遍历步骤，并给出视频证据”，但输入给模型的材料还没有准备好。模型不会因为数据库有视频地址，就自动理解整段课程。

## 1 先区分原始数据和模型输入

视频由画面和音频组成。ASR 把语音识别成文字，OCR 从图片识别文字，FFmpeg 负责提取、切分和转换音视频。模型分析使用什么材料，要看后端实际传了什么。

项目在这里走的是先建立统一视频上下文的路线。ASR、OCR 和文字模型各自承担不同工作，不能把“FFmpeg 已运行”当成“已经理解视频”。

例如老师说“先访问根节点”，画面写着“前序遍历：根左右”。语音与画面文字结合，比任意一条单独输入更有帮助。不过图形关系、口音或模糊板书也可能造成识别遗漏。

## 2 为什么要切片并保留时间

长音频切片后可以分段处理，局部失败更容易定位；关键帧提供画面文字和可核对图片。当前 `VideoContextService` 按 60 秒组织片段，画面抽取还有场景变化与 30 秒保底间隔相关逻辑。切片长度、帧采样间隔、后续检索分块是不同概念，不能混成一个参数。

最终要保留每段材料来自何时。否则“前序遍历是根左右”这句话虽然可能正确，却不能说明视频里具体哪段支持它。

## 3 读懂一个数据类

[VideoContext](../../../server/src/main/java/com/example/server/dto/VideoContext.java) 是 Java record，可以先理解为一组有名字的数据字段。它把视频来源、当前目标和片段列表放在一起。片段包括：

```java
public record VideoSegment(
    long startMs,
    long endMs,
    String transcript,
    List<String> ocrTexts,
    List<String> evidenceFrames) {}
```

上面摘出字段展示，源码还包含构造校验。`long` 保存整数时间，`String` 保存文字，`List<String>` 是字符串列表；`Ms` 表示毫秒，120000 毫秒就是 120 秒。

教学片段可以写成：

```json
{"startMs":120000,"endMs":180000,"transcript":"先访问根节点，再处理左子树和右子树","ocrTexts":["前序遍历：根左右"],"evidenceFrames":["frame_000125.jpg"]}
```

这一示例与项目离线样例的主题一致，具体素材内容只用于说明结构。列表让一段时间可以包含多条画面文字和多张证据图片。

## 4 统一结构怎样帮助后续开发

如果 Agent 每次都直接读取某个识别供应商的原始返回，供应商字段一改，分析代码也可能跟着改。统一上下文把这种差异收敛在资料准备阶段，后续只处理约定的数据结构。

统一不等于没有信息损失。只提取文字可能无法完整表达动画和图形关系；用户问到材料未覆盖的细节时，后端应保留证据边界，不能把模型猜测当作识别结果。

## 5 并行与失败怎样影响资料

语音与画面可以用不同线程池处理。线程池限制同时工作的数量，避免每来一个任务就无限创建线程。并行的收益取决于机器资源和外部服务配额，并不保证两条分支同时瞬间完成。

阅读时找出某分支失败后的处理：是否保留另一条成功材料、是否记录警告、什么情况下整个上下文构建失败。不要把“有降级”理解为“任何错误都能忽略”。

## 6 练习与参考答案

从 `VideoContextService.build` 找到两条分支，再沿 `OcrUtils` 和转写服务看各自如何产出文字。把单位写在纸上，防止把秒和毫秒混用。

问：OCR 把“根左右”识别成“根右左”，Critic 能保证纠正吗？答：不能，检查也可能依赖错误材料。需要正确的基础识别、其他证据或明确提示不确定性。

问：为什么保留图片文件引用而不只留 OCR 文本？答：文字提取不一定完整，图片引用能够帮助后续核对证据或展示来源；实际怎样使用仍要看下游实现。
