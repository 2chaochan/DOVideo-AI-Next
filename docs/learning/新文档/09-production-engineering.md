# 09 怎样验证并维护 Agent 后端

模型生成内容有不确定性，后端仍然需要确定的接口、权限、状态规则和恢复流程。工程保障的目标是：出现问题时能定位，修改后能验证，发布后能维护。

## 当前已有的基础

项目已经有后端回归测试、ArchUnit 分层检查、Spotless 格式检查、Flyway 数据库迁移和 GitHub CI，也有资源并发限制、检查点及失败任务处理。先理解这些机制解决的问题，再做小范围改造。

在 `server` 目录运行：

```powershell
./mvnw.cmd -s .mvn/central-settings.xml verify
```

测试可能故意制造异常，判断通过与否应看报告中的失败、错误及跳过数量。业务测试通过也不等于已经完成真实模型、数据库和对象存储联调。

## 测试分三层理解

单元测试通常替换外部依赖，检查某个业务分支。数据库集成测试检查真实 SQL 和事务。端到端验证则沿着上传、提交分析、获取进度和读取结果检查整条链路。

上传幂等改造已经展示前两层：故障注入检查重试行为，H2 SQL 测试检查约束和回滚。真实 MySQL 和 MinIO 的故障行为仍需要相应环境验证。

## 故障时先找哪几个信息

记录用户可见现象、`mediaId`、目标、模式及发生阶段，再从接口日志追到消费者和 Agent 阶段日志。查看消息是否积压、依赖是否可用、预算是否耗尽。避免看到一个超时就盲目增加全部重试次数。

当前 `/health` 固定返回 `UP`，主要说明接口能够响应，不能据此判断所有依赖可用。生产就绪检查、指标告警和统一链路追踪属于继续完善的方向。

## 每次修改怎样形成学习成果

在独立分支记录问题、触发条件、方案、测试与剩余边界。先跑涉及模块的验证，再按贡献规范完成提交。数据库变更新增迁移文件，原始迁移保留历史；许可证和原作者来源声明继续保留。

入口：[贡献规范](../../../CONTRIBUTING.md)、[Git 工作流](../../development/git-workflow.md)、[上传幂等改造记录](../../development/upload-idempotency.md)。

自测：你能否用“一个具体故障、一个代码修改、一个可重复验证的结果”讲清楚这次上传幂等改造？这就是后续每篇实践笔记应达到的标准。
