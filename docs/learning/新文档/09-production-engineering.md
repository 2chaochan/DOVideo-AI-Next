# 09 把一次改动变成可验证的后端能力

学习到这里，你应该能解释从请求到结果的过程。接下来要解决的是：修改一个环节后，如何知道没有破坏别的环节；发生故障时，怎样找到原因。

## 1 先理解测试的输入和断言

测试不是运行几次看页面能打开。它应给定准备条件、执行动作，并检查明确结果。断言就是程序化的检查，例如“同一 uploadId 最终只有一条媒体记录”。

单元测试经常用 Mock 替换外部依赖。Mock 可以预先设定“Redis 写入时抛异常”，用于稳定验证业务分支。但它不能证明真实 Redis 的连接、锁和过期行为完全正确。

数据库测试运行真实 SQL 检查约束和事务。上传仓储测试使用 H2 MySQL 模式，证明该环境中的媒体插入与凭据插入共同回滚；真实 MySQL 的全部迁移、运行配置仍要在对应环境验证。

端到端验证则从用户操作走完整链路，需要更多实际依赖。三种测试回答不同层次的问题，不是相互替代的名称。

## 2 一个故障测试怎样读

打开 `ChunkUploadServiceTest` 的 `lostAcknowledgementAfterDatabaseCommitDoesNotCreateAnotherMedia`。准备阶段让仓储表现为“完成记录已存在，但调用抛出连接异常”，动作是再次提交完成请求，断言是复用原媒体且不再保存。

这个测试验证提交确认丢失后的业务行为，不是实际杀死数据库进程。读笔记时也要把模拟条件和真实联调条件分别写清楚。

## 3 验证命令和报告

在项目根目录打开 PowerShell，进入后端：

```powershell
cd server
./mvnw.cmd -s .mvn/central-settings.xml '-Dtest=ChunkUploadServiceTest,ChunkUploadRepositoryTest' test
./mvnw.cmd -s .mvn/central-settings.xml verify
```

第一条测试命令聚焦上传；第二条执行完整后端验证，包括现有测试和构建期检查。测试报告在 `server/target/surefire-reports/`。检查失败、错误和跳过数量，不要因为故障注入打印了异常堆栈就直接判失败。

上传改造提交 `3b20e54` 当时的记录是上传相关 14 项、完整后端 75 项测试通过。这个数量属于该次代码验证，本轮文档重写没有重新执行业务测试。

## 4 日志 指标和跟踪分别看什么

日志记录一次事件，例如任务进入检查阶段；指标汇总失败率、耗时分布或队列积压；跟踪把同一任务跨请求、消息和模型阶段的工作关联起来。

当前 `AgentTelemetry` 已记录一些阶段与估算消耗。排障时先拿到媒体、目标、模式和阶段，再沿提交侧、消费者、Agent 日志找线索。只看最后一个“超时”错误，可能错过最早的依赖故障。

`/health` 固定返回 `UP` 说明该接口能响应，不说明数据库、队列和模型都可用。更完整的生产就绪检查、告警与跨边界跟踪是后续方向。

## 5 数据库迁移和发布

迁移文件让数据库结构变更按版本执行。新增完成凭据表写在 V4 中，已有迁移保留。不要随意修改已经在其他环境执行过的迁移，否则环境历史可能无法对应。

数据库事务与应用发布也不是一件事。发布前需备份、确认迁移权限和应用兼容性，并知道回退旧应用时哪些新表需要保留。项目 Compose 当前主要组织中间件，不等于已经提供全部生产发布流程。

## 6 本章练习与参考答案

练习：用五句话描述一次上传幂等改造，分别写问题、触发条件、方案、验证、剩余边界。可以在 [实验记录目录](experiments/README.md) 保存自己的观察。

参考：原来数据库成功而 Redis 凭据未写入时可能重复插媒体；同一上传完成请求重试触发；新增数据库凭据并原子提交；用 SQL 事务和服务故障测试验证；对象存储不参与事务、真实中间件联调还需相应环境。
